Change management

How to use the architecture during development.

1. Identify authorityWhich project owns the state, API, event, schema or lifecycle being changed?
2. Follow outgoing edgesList direct consumers, external adapters and tooling contracts.
3. Review transitive impactCheck whether downstream projects expose that state again to another project.
4. Test as a groupRun targeted compatibility tests before merging or releasing any linked project.
Example: HelperProfiles role schema changeHelperProfiles → review HelperPayroll → review RemoteDispatcher → test planned AvatarSwitcher contract. No expected impact on CCO, PrecisionNutrition, SaveUnitProfiles, StopTime or Silo Fill Limit unless new coupling has been introduced.
Example: CCO save-state / reporting changeCropControlOverride → CCO regression tests → Farm Sim Manager compatibility test → parser validation → UI/state presentation validation.
Example: AutoDrive or Courseplay upstream updateUpstream mod → RemoteDispatcher adapter review → invocation/state detection tests → generic RemoteDispatcher behaviour should remain unchanged if the adapter boundary is clean.

Architectural priorities

  • HelperProfiles should be treated as a worker-domain platform. Worker identity, role and lifecycle contracts should be explicit and versioned.
  • RemoteDispatcher should isolate third-party automation. Prefer provider/adaptor interfaces for AutoDrive and Courseplay.
  • PrecisionNutrition should consume stable forage contracts. Silage Realism and Managed Pastures should publish data rather than directly modify nutrition internals.
  • CCO should treat Farm Sim Manager compatibility as part of its public support surface. Data representation changes can be breaking changes even when CCO remains functional in-game.
