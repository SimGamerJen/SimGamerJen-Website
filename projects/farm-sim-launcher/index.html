The idea

Move setup out of the loading screen.

Farming Simulator saves often depend on much more than the save folder itself: a particular mod set, regional unit choices, map-specific rules and a known starting state. The launcher project is intended to bring those decisions together before the player enters the game.

Rather than trying to preserve or reverse-engineer whatever field state FS25 happened to create, the chosen first-load model is deliberately deterministic: the desktop app defines the desired world and a lightweight runtime component applies that setup when the generated save loads for the first time.

Planned capability

One workspace around the save.

The scope is intentionally modular. Features can mature independently without requiring the launcher to become a monolithic replacement for the game.

First-load architecture

The desktop app defines it. FS25 applies it.

The bootstrap only exists to bridge the desktop configuration into game-side systems that can safely manipulate the loaded world.

1. ConfigureChoose map, save settings, mod environment and starting rules.
2. GenerateCreate the initial save structure and first-run configuration.
3. LaunchStart FS25 with the correct managed mod environment.
4. BootstrapDetect the generated save’s first load and apply the requested setup.
5. Hand offNormal save lifecycle begins; CCO and other mods continue ongoing control where appropriate.

Relationship to SGJ mods

Integration instead of duplication.

The launcher is not intended to absorb Crop Control Override or other established SGJ mods. The desktop side can expose a simplified setup experience, while the game-side mod remains responsible for the richer controls during the save lifecycle.

That approach also gives the launcher room to bring together diagnostic utilities—such as mod comparison and save inspection—without turning every utility into part of the FS25 runtime.
